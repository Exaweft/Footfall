Footfall user guide

Footfall records where players move, die and trigger events during playtests, saves each session to a local file, and draws it in your Scene View: markers, trails and a density heatmap. It works in the Editor's Play Mode and in development builds, and is off in release builds unless you turn it on.

1. Quick start

  1. Install. In the Package Manager's My Assets, download and import Footfall; it goes into Assets/Footfall. Check the Console is free of errors. It needs Unity 6 (6000.0 or newer) and no other packages.
  2. Record movement. Select your player and add the Heatmap Recorder component (Add Component > Exaweft > Footfall > Heatmap Recorder, or search for it). It samples the player's position every half second.

  3. Record an event. Where your player dies, add one line. Here Die stands for your game's own death code; call Heatmaps.Record wherever that is:

    using Exaweft.Footfall;
using UnityEngine;

public class PlayerHealth : MonoBehaviour
{
    void Die(string killer)
    {
        Heatmaps.Record("death", transform.position, "enemy", killer);
    }
}
  1. Play. Enter Play Mode, play for a minute and die a few times, then stop. Footfall saved the session to a file.
  2. Look. Open Tools > Exaweft > Footfall > Sessions and press Editor Sessions. Then, in the Scene View, turn on the Footfall panel: with the pointer over the Scene View, press the ` key to open the Overlays menu and click Footfall. Your path shows as a trail and each death as a red marker. Tick Density and press Top View to see where deaths cluster.

To try it without writing any code first, open the Demo sample (section 14): it comes with eight ready-made sessions.

No player yet, as in a new empty project? Add a Capsule, give it the Heatmap Recorder, and use this stand-in, which walks in a circle and dies every five seconds:

using Exaweft.Footfall;
using UnityEngine;

public class WalkAndDie : MonoBehaviour
{
    float nextDeath = 5;

    void Update()
    {
        float t = Time.time * 0.5f;
        transform.position = new Vector3(Mathf.Cos(t) * 6, 1, Mathf.Sin(t) * 6);
        if (Time.time > nextDeath)
        {
            Heatmaps.Record("death", transform.position, "enemy", "spikes");
            nextDeath += 5;
        }
    }
}

2. Recording events

Heatmaps.Record(name, position) records that something happened at a world position. The name is your own: use "death", "checkpoint", "jump", "purchase", or anything else worth seeing on the map. Each name gets its own colour in the Scene View, and the name "death" is also counted in the Sessions window's Deaths column.

Events can carry tags, as key and value strings, to say more about what happened:

Heatmaps.Record("death", pos);                                       // no tags
Heatmaps.Record("death", pos, "enemy", "bat");                       // one tag
Heatmaps.Record("death", pos, ("enemy", "bat"), ("wave", "3"));      // any number of tags

Tags show when you click a marker, and the panel's Tags card counts events by any tag (deaths per wave, say) and can show only one value (section 7).

  • Calls can come from any script, at any time. If no session is open, the first call starts one.
  • Calls do nothing in release builds (section 10), so you can leave them in your code.
  • For 2D games, record positions with z = 0; Footfall then draws on the XY plane.

3. Recording movement

Add Heatmap Recorder to anything whose path you want to see: usually the player, but also enemies, vehicles or NPCs. Each recorder is one track in the session, drawn as one trail. A GameObject takes one recorder.

SettingWhat it does
Sample IntervalSeconds of game time between samples. Default 0.5; at least 0.05.
Track NameThe trail's name, such as "Player". Empty uses the GameObject's name.

You can also add it from code, for objects spawned at runtime:

var recorder = enemy.AddComponent<HeatmapRecorder>();
recorder.TrackName = "Enemy " + number;
recorder.SampleInterval = 1f;

Samples use scaled game time, so a paused game (Time.timeScale = 0) records nothing.

4. Sessions

A session is one file holding one play of one scene.

  • It starts on the first event or sample.
  • It ends when the active scene changes, when the game quits or leaves Play Mode, or when you call Heatmaps.EndSession(). Call that yourself to split sessions, for example at the end of each run of a level.
  • Files go to Application.persistentDataPath/Footfall/Sessions, one .footfall file per session. Change Heatmaps.OutputFolder to use another folder. Project Settings > Exaweft > Footfall shows the folder.
  • Writes are buffered and saved every two seconds, so a crash loses at most the last two seconds. Heatmaps.Flush() saves straight away.

Useful settings, all read at the start of the next session:

PropertyUse
Heatmaps.TesterLabelA name saved with the session, such as "Sam" or "Discord-3". Also set by starting the game with -footfallTester "Sam".
Heatmaps.PausedWhile true, nothing is recorded. Use it to skip menus and cutscenes, or to record only after a tester agrees.
Heatmaps.MaxPositionSamplesThe most samples a session keeps (default 100,000, about 14 hours of one recorder).
Heatmaps.MaxEventsThe most events a session keeps (default 20,000). Kept apart from samples, so long sessions never lose their deaths.

Heatmaps.IsRecording, Heatmaps.CurrentSessionPath, Heatmaps.LastSessionPath and Heatmaps.SessionTime tell you what is happening, for example to show testers where their file went.

5. Collecting sessions from testers

Testers need nothing but your development build. There is no server, account or upload.

  1. Send a development build (Build Profiles > Development Build). Release builds record nothing unless you turn recording on (section 10).
  2. Ask testers to start the game with a label, such as a shortcut ending in -footfallTester "Sam", or set Heatmaps.TesterLabel from your own name prompt.
  3. Ask them to send you the files in their sessions folder: Application.persistentDataPath/Footfall/Sessions. On Windows that is %USERPROFILE%\AppData\LocalLow\<company>\<product>\Footfall\Sessions.
  4. Put everyone's files in one folder and use Import Folder… in the Sessions window. Subfolders are included.

6. The Sessions window

Tools > Exaweft > Footfall > Sessions lists the sessions you have loaded. Every session in the list is drawn in the Scene View, unless a filter hides it.

  • Import File… adds one .footfall file; Import Folder… adds every file in a folder and its subfolders.
  • Editor Sessions adds the sessions recorded in this Editor's Play Mode.
  • Reload reads every loaded file again; Clear empties the list. Files are never deleted.
  • Filters: Scene, Build, Tester, Has event (only sessions with that event) and a From–To date range. Reset shows them all. The line under the filters totals what's shown: sessions, testers, time played and deaths.
  • Columns: Started, Scene, Tester, Build, Duration, Events, Deaths and Notes.
  • Notes flag sessions that ended without closing (the game stopped or crashed; data up to the last save is kept) or that reached a cap.
  • Right-click a session to replay it in the Scene View, show its file in Explorer or Finder, or remove it from the list. Double-click also replays it.

The list is kept with your project (in UserSettings), so it is still there after a restart.

7. The Footfall panel

Turn it on from the Scene View's Overlays menu (the ` key over the Scene View). It has four cards. Collapsed, it shows as the footprint icon.

Show

  • Points: a marker at every event, coloured by event type. Trails: each track's path. Density: the heatmap grid (section 8).
  • This scene only: show only sessions recorded in the scenes you have open. Untick it to see sessions from any scene, for example when a level was renamed.
  • The chips count the sessions and events shown. Below them, the legend lists each event type with its count; click one to hide or show its markers.
  • Click a marker in the Scene View to see here what it was, when, its tags, and its tester, scene and build.

Tags (shown when the loaded events have tags)

  • Tag: pick a tag key, such as wave or enemy, to count the shown events by its values.
  • Show: pick one value to show only those events: markers, the legend and event density. (all) shows every value.

Density (shown when Density is ticked): see section 8.

Replay: see section 9.

Below the cards: Top View, Export PNG… and Sessions Window.

8. Density heatmaps

The grid counts what happened in each square and colours it from quiet to busy.

SettingWhat it does
CountsWhat the grid counts: one event type, such as death, or Movement for where players spent their time.
Cell sizeThe width of each square, in world units.
Floor gapPoints in one square this far apart in height count as separate floors, each drawn at its own height. 0 keeps one flat grid. Default 2.5.
ColoursHeat, Viridis (readable with most colour blindness) or Red.
OpacityHow much of the level shows through.
PlaneXZ (the ground of a 3D level), XY (a 2D level), or Auto: XY when every point has z = 0.

The line below the settings says how many events fill how many cells, and the count in the busiest cell.

9. Replay, Top View and Export PNG

  • Replay one session: pick it in the Replay card (or double-click it in the Sessions window), then drag the scrubber or press Play. Markers appear as they happen and the trail grows. Stop shows every session again. The speed menu plays at 1x to 16x.
  • Top View looks straight down on everything Footfall draws, sized to fit (or straight on, for 2D).
  • Export PNG… saves the Scene View as you see it, overlays included, as a PNG for Discord, a devlog or a design review.

10. Release builds and performance

  • Off in release builds. Recording runs in the Editor and in development builds. In a release build every Heatmaps call does nothing and Heatmap Recorder turns itself off, so you can leave them in. A call that does nothing still costs one check, and, as with Debug.Log, your arguments are still worked out before the call: a string built for a tag, say. If an argument is costly to work out, wrap the call in if (Heatmaps.IsEnabled).
  • Bad positions are skipped. A position that isn't a finite number (NaN or infinity, usually a bug elsewhere in the game) is not recorded, with one warning per run.
  • Recording a release build, such as a closed playtest build: tick Record in release builds in Project Settings > Exaweft > Footfall. It adds the FOOTFALL_RECORD_IN_RELEASE scripting define for the current build platform, so set it again after switching platform. Heatmaps.IsEnabled says whether recording runs.
  • No allocations while recording, after the first use, as long as the event names and tags you pass are existing strings (literals or cached), not strings built on each call. The tuple form of Record builds a small array each call; to avoid that, keep a HeatmapTag[] and pass it.
  • Small files. A sample is one short text line. An hour of one recorder at 0.5 s is about 7,200 lines.

11. The session file format

Session files are UTF-8 text, so you can open them in any editor or read them in your own tools.

  • Line 1 is a JSON header: format and version, Footfall version, session ID, scene and scene path, build version, Unity version, platform, whether it was the Editor or a development build, tester label and start time (UTC).
  • Each later line is a record: a letter, then tab-separated fields. T declares a track, P is a position sample, E is an event with its tags, C notes that a cap was reached and X ends the session.
  • Every file carries a format version (1 for this release). Later versions of Footfall will still read version 1 files.

To read sessions in your own Editor tools, use SessionFile.Read(path), which returns a SessionData with the header, tracks, samples and events.

12. What has been tested

  • Unity versions: 6000.0.85f2 and 6000.5.9f1, on Windows.
  • Render pipelines: Built-in and URP. Footfall draws in the Editor only, with no shaders of its own, so it doesn't depend on the render pipeline.
  • Games: a 2D shooter, Unity's FPS Microgame (3D, several floors) and a 3D management game with up to 21 tracks at once, plus the Demo sample.
  • Recording: in the Editor's Play Mode. Development and release builds use the same code path, switched by the setting in section 10.

13. Known limitations

  • The density grid counts squares on a plane, split into floors by height. It is not a 3D volume.
  • Very long trails are thinned to 2,000 points each when drawn. The file keeps every sample.
  • Recording uses Unity's main thread and scaled game time; nothing is recorded while Time.timeScale is 0.
  • Sessions are local files. Collecting them from testers is up to you (section 5).

14. The Demo sample

The Demo sample is in Assets/Footfall/Samples/Demo, imported with the rest of Footfall. It has a small 3D level, "The Crossing", built from Unity primitives, simulated players and eight ready-made sessions. Its README walks through the panel.
